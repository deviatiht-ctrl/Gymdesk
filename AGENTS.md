# Project verification and runtime requirements

- Run Flutter commands from this directory, not its parent `GYM`. On this workstation the user uses `D:\flutter\flutter\bin\flutter.bat`; Deno is `.tools\deno\deno.exe`.
- Flutter verification: `flutter test --no-pub` and `flutter analyze --no-pub`. Existing deprecation notices in `badges_page.dart` and `language_selection_page.dart` are outside the email/enrollment code. The full test suite currently has two unrelated attendance failures: tests expect `granted`, while the scanner emits `granted_in` / `granted_out`.
- Email backend verification: `.\.tools\deno\deno.exe check supabase/functions/send_emails/index.ts` and `.\.tools\deno\deno.exe test --allow-read --allow-env supabase/functions/create_gym_owner/handler_test.ts supabase/functions/manage_staff/handler_test.ts supabase/functions/send_emails/handler_test.ts supabase/tests/email_migration_test.ts`.
- The email migration test uses pinned PGlite in memory, applies the existing SQL chain, then applies `14_email_enrollment.sql` twice and executes rollback-only assertions. It supplies minimal Auth/Storage schemas and omits optional pgcrypto; it does not verify Supabase HTTP services, pg_cron, pg_net, or actual Brevo delivery. SQL assertions must only run on a disposable database.
- Production SQL files in `supabase/sql` are applied manually in README order. Apply `14_email_enrollment.sql` after `13_v2_sync.sql`, then `15_admin_offers.sql` (admin offer catalog, `platform_register_payment`, `platform_gym_overview`, and the `current_gym_id()` fix that lets trial/grace gyms sync); it is idempotent. `supabase db push` does not apply these files automatically. `supabase/tests/admin_offers_test.ts` verifies the payment RPC end-to-end on PGlite.
- The email worker requires server-only `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, optional `BREVO_SENDER_NAME`, and a strong random `EMAIL_WORKER_TOKEN`. The sender/domain must be verified in Brevo. Never place these secrets in Dart, logs, or source control.
- Deploy `send_emails` with platform JWT verification disabled because cron authenticates using `x-email-worker-token`, validated inside the handler. Enable pg_cron and pg_net; configure Vault secrets `gymdesk_email_worker_url` (the deployed function endpoint) and `gymdesk_email_worker_token` (same value as `EMAIL_WORKER_TOKEN`). Apply/reapply migration 14 after enabling those extensions so it registers the minute scheduler. Do not trigger live email sends without specific user confirmation.
- `email_delivery_settings.daily_limit` defaults to 300 for the entire Brevo account, not per gym. Reservations over a rolling 24-hour window are deliberately conservative. Set a different limit only to match the actual Brevo plan; sends outside GymDesk also consume provider credits. `not_enough_credits` pauses the queue for 24 hours without deleting jobs.
- `email_outbox.sent` means accepted by Brevo, not delivered to the inbox. `uncertain` means an interrupted request may already have been accepted: check Brevo logs before manually requeuing it. Confirmed permanent errors remain `failed` for correction. No automatic resend of ambiguous outcomes is attempted.
- Imported paid periods use `subscriptions.opening_credit`, never synthetic cash payments. Every balance calculation must subtract that credit. Enrollment price includes the first plan period; renewals always use `plans.price`.
