# Project verification and runtime requirements

- Run Flutter commands from this directory, not its parent `GYM`. On this workstation the user uses `D:\flutter\flutter\bin\flutter.bat`; Deno is `.tools\deno\deno.exe`. If `D:\flutter` is unavailable, a bundled Dart SDK exists at `.tools\flutter\bin\cache\dart-sdk\bin\dart.exe`.
- Suprema BioMini reader: the real USB VID/PID is `0x16D1/0x0409` (an old `0x1612` guess still appears in `gymdesk_biometrics` for legacy entries). `tools/access_agent/agent.dart` (build with `dart compile exe … -o GymDesk_USB/access_agent.exe`) loads `UFScanner.dll`/`UFMatcher.dll` directly when they match the agent's architecture; for the common **32-bit** BioMini DLLs it spawns `tools/access_agent/bridge32/SupremaBridge32.cs` compiled x86 as `suprema_bridge32.exe` next to the agent. The bridge runs **one command per process via argv** (`<dllDir> status|capture|verify|identify`) because Dart-spawned .NET processes never receive stdin on Windows; `identify` reads candidates from a temp file. Rebuild the bridge with `csc -platform:x86`. The agent must never report `reader_connected: true` when SDK or hardware detection fails — no simulated captures.
- Flutter verification: `flutter test --no-pub` and `flutter analyze --no-pub`. Existing deprecation notices in `badges_page.dart` and `language_selection_page.dart` are outside the email/enrollment code. The full test suite passes (82 tests). Bundled Flutter: `.tools\flutter\bin\flutter.bat` (call it as `./.tools/flutter/bin/flutter.bat` from Git Bash).
- Email backend verification: `.\.tools\deno\deno.exe check supabase/functions/send_emails/index.ts` and `.\.tools\deno\deno.exe test --allow-read --allow-env supabase/functions/create_gym_owner/handler_test.ts supabase/functions/manage_staff/handler_test.ts supabase/functions/send_emails/handler_test.ts supabase/tests/email_migration_test.ts supabase/tests/email_delivery_fix_test.ts`.
- The email migration test uses pinned PGlite in memory, applies the existing SQL chain, then applies `14_email_enrollment.sql` twice and executes rollback-only assertions. It supplies minimal Auth/Storage schemas and omits optional pgcrypto; it does not verify Supabase HTTP services, pg_cron, pg_net, or actual Brevo delivery. SQL assertions must only run on a disposable database.
- Production SQL files in `supabase/sql` are applied manually in README order. Apply `14_email_enrollment.sql` after `13_v2_sync.sql`, then `15_admin_offers.sql` (admin offer catalog, `platform_register_payment`, `platform_gym_overview`, and the `current_gym_id()` fix that lets trial/grace gyms sync); it is idempotent. `supabase db push` does not apply these files automatically. `supabase/tests/admin_offers_test.ts` verifies the payment RPC end-to-end on PGlite.

It widens `email_outbox.kind`, fixes `gym_member_limit()` (20 referenced a missing `platform_offers.sort_order`), puts `logo_path` + `reply_to` (gym email, else owner login email) in every member payload, schedules `process_daily_reminders()` daily at 12:00 UTC, adds `campaign_send_members` (server-side campaigns), and the super-admin-only `platform_email_config` (`platform_email_config_get/set`, worker reads it through service-role `email_worker_config()`). - BioEntry W2 facts verified on the real terminal (544283675, 192.168.1.41:51211, `templateFormat=SUPREMA`): `BS_SDK_SUCCESS` is **1** (not 0); identify only matches users with **2 templates per finger** (enroll duplicates a single one); user `startTime=0/endTime=0xFFFFFFFF` is treated as expired (`ACCESS_DENIED` sub 0x03) — use 978307200 → 1924991999 (BioStar defaults) or the subscription end. `ACCESS_DENIED` events still carry the uid, which the app-control mode relies on (`expiredEnd` = 2001-01-01).
- Access agent 3.4.0 keeps one `biostar_tool watch <ip> <port> 0 <cmdDir>` process alive (events → `/api/events/poll` long-polling; door `pulse/release/lock` go through `*.cmd` files on the same connection). Every other `biostar_tool` call pauses the watcher first (one SDK connection at a time). `lib/core/access_control/terminal_access_service.dart` builds the W2 payload per mode (`terminal_enforces_expiry`, `app_controls_door` in `gyms.biometric_config`) and decides on events; `/access-display` (2nd screen) runs it and auto-syncs every 10 min. Tests: `test/terminal_access_test.dart`.
- No Brevo key or Brevo wording in gym-owner UI: the Flutter app never calls Brevo. The super admin sets the key/sender in `/admin/email`. Member emails go out with sender name = gym name, sender address = platform verified sender, `replyTo` = gym email, plus a text part.
- The email worker requires a strong random `EMAIL_WORKER_TOKEN`; the Brevo key/sender come from `platform_email_config`, falling back to server-only `BREVO_API_KEY`, `BREVO_SENDER_EMAIL`, optional `BREVO_SENDER_NAME`. Optional `GYMDESK_LOGO_URL` (https) for the platform welcome email. The sender/domain must be verified in Brevo. Never place these secrets in Dart, logs, or source control.
- Deploy `send_emails` with platform JWT verification disabled because cron authenticates using `x-email-worker-token`, validated inside the handler. Enable pg_cron and pg_net; configure Vault secrets `gymdesk_email_worker_url` (the deployed function endpoint) and `gymdesk_email_worker_token` (same value as `EMAIL_WORKER_TOKEN`). Apply/reapply migration 14 after enabling those extensions so it registers the minute scheduler. Do not trigger live email sends without specific user confirmation.
- `email_delivery_settings.daily_limit` defaults to 300 for the entire Brevo account, not per gym. Reservations over a rolling 24-hour window are deliberately conservative. Set a different limit only to match the actual Brevo plan; sends outside GymDesk also consume provider credits. `not_enough_credits` pauses the queue for 24 hours without deleting jobs.
- `email_outbox.sent` means accepted by Brevo, not delivered to the inbox. `uncertain` means an interrupted request may already have been accepted: check Brevo logs before manually requeuing it. Confirmed permanent errors remain `failed` for correction. No automatic resend of ambiguous outcomes is attempted.
- Imported paid periods use `subscriptions.opening_credit`, never synthetic cash payments. Every balance calculation must subtract that credit. Enrollment price includes the first plan period; renewals always use `plans.price`.
